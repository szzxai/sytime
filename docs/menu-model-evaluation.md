# DeepSeek 菜谱识别试验

2026-11-21 使用 `https://sub2api.zquant.site/v1` 实测。模型列表给出的实际 ID 为 `deepseek-v4.1-flash-1017`。

## 接口要求

- 支持图片输入与 Chat Completions。
- `json_schema` 返回 HTTP 400，需设置 `MENU_RESPONSE_FORMAT=json_object`，继续由本地 Ajv 严格校验。
- 测试使用 `MENU_THINKING=disabled`。默认思考模式曾耗尽小额度输出预算，导致 JSON 截断。
- 随机标识图片的八字段能力测试通过，约 4 秒。

## 真实菜单结果

输入为学校文章 11427（2026-10-26 至 2026-10-31 菜单）的原始图片，采用与 Gemini 相同的分组识别和复核流程。

面档表格共 42 个菜品格，两个地点展开为 84 条供应。根据原图人工转录后，对日期、星期、餐次、地点、档口、名称、价格及辣椒字段逐项比对，84/84 条完全一致。该表调用两次模型，输入 4,169 tokens，输出 2,098 tokens。此结果仅代表这张表。

整图测试调用 39 次模型后失败：模型将部分日期没有菜品的正常空白列报告为“未读清”，重试仍然无法通过完整性检查。测试没有发布数据，也没有修改现有菜单。面档样本通过并不代表整篇菜单可稳定同步。

旧的兼容接口分块流程在同一面档表格中出现漏行与地点合并错误，被覆盖复核拦截。因此正式 worker 已统一使用现有 Gemini 的分组流程，提供商只负责模型传输。

## 提示词优化复测

同日进行四版提示词对比，模型、JSON模式、思考模式设置保持一致，每次创建新客户端，不使用本地识别结果缓存。第二版将“空白”“可读”“确实模糊”分开定义，并要求问题数组仅包含未解决问题；第三版进一步明确免费分类的价格优先级、并列地点拆分及普通分类的地点继承；第四版加入项目既有地点词汇用于校对字形，并明确局部餐次标签和完整档口标签的优先级。读取、重试和复核使用同一字段规则，重试保留上一轮候选与来源上下文。

| 测试 | 原提示词 | 第三版提示词 |
| --- | --- | --- |
| 11427 夜宵，人工核对18条供应，重复3次 | 2次18/18；1次把两个地点合为一个，9条全字段不匹配 | 3次均18/18，无额外供应 |
| 11427 面档，人工核对84条供应，重复2次 | 前次单次84/84 | 2次均84/84，无额外供应 |
| 11408 周一复杂菜单，人工抽样18条供应，重复3次 | 未进行同条件对照 | 3次均18/18；整张裁片共输出62、65、65条，非抽样部分仍有差异 |

11408 的抽样覆盖午/晚餐、多个共用地点、辣椒、免费汤及“1元/1.5元”价格应为null的情况。这张裁片采用事先确定的边界，附带原图完整标题，仅测读取与复核。最初让模型重新定位人工裁片时发生了二次裁切错误；该试验不计入上述固定边界结果。测试数据不用于提示词中的菜名或答案示例。

第二版曾成功读取11427整图，输出957条，但额外菜单试验发现免费汤为null和共用地点遗漏，故未采用。第三版整图两次独立复测均通过，均输出966条，分别耗时148秒和154秒、调用33次和34次。但两次八字段完全一致的记录仅484条。新增人工转录的周一早餐80条供应，第三版两次分别仅0/80和40/80完全匹配：地点专名误读及早餐分类为空影响了大量记录。因此继续进行第四版试验，不能以总条数相同判断稳定。整图没有逐格人工建立完整真值，记录数相同或模型自我复核通过都不能证明全部字段正确。

剩余差异已定位到复杂局部标签：例如“泮水居二楼风味&紫阳楼风味”的地点集合，以及位于午餐表中的“晚上套餐”应采用哪一层餐次标签。固定边界重复测试中，这些非抽样字段仍会变化；不能仅凭18条抽样全部正确就将整张裁片视为稳定。

### 第四版定向结果

采用地点词汇和局部标签规则后，夜宵18条连续3次全部匹配，面档84条连续2次全部匹配；11408周一复杂菜单的18条人工抽样供应连续3次全部匹配。其完整裁片三次均输出65条，其中62条八字段完全一致；去掉档口group字段后63条一致。因此剩余波动已缩小，但仍未完全消失，不能把抽样通过解释为整张裁片100%准确。

第四版整图两次独立复测均通过，均输出966条，分别耗时181秒和166秒，调用35次和33次；本地缓存命中均为0。人工按原图核对的182条供应（周一早餐80条、面档84条、夜宵18条），两次均182/182八字段完全匹配。相同样本在第三版整图输出中分别仅102/182和142/182匹配。

两次第四版整图有954/966条八字段完全一致；其余12条全部只差档口名称中“&”两侧的空格，其余七字段全数一致。仅统一这类空格后两份966条记录完全相同。这是同一张图的重复一致性，不能当成全部966条的真实准确率。原始报告和每次输出保存在本地`output/deepseek-prompts/`，汇总为`final-report.json`。最终源码使用`menu_table_v9`和`menu_table_review_v11`，表头读取同时使用地点词汇校对；这些版本名参与缓存身份，避免复用旧提示词结果。

## 当前选择

最终第四版提示词改善了本次空白列误报、食堂专名、抽样免费价格及共用地点问题，已用于OpenAI兼容接口；Gemini保留原有读取、复核提示词。完整性检查、JSON Schema校验和失败文章不发布规则没有放宽，完全空白的整篇菜单仍拒绝发布。测试没有更改线上数据或服务端密钥配置。

保留Gemini默认提供商。DeepSeek现已能稳定跑通本次整图，可作为可配置候选试运行；但另一周菜单仍有“食堂”和“食堂一楼北厅”这类局部地点层级差异，且尚未建立跨多周的完整人工真值，因此本轮不修改默认提供商或部署密钥。配置方法与独立图片验证命令见[部署说明](./deployment.md#菜谱识别模型)。
