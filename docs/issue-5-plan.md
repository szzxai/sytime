# Issue #5 实施计划

本计划记录用户确认的范围，替代 UI 预设计中菜品详情页、Python 运行服务和固定同步时间的假设。原始需求保留在 [里程碑快照](../PLAN_2026-10-01.md)。

1. 从 `../szzx-menu` 的十篇历史识别结果生成版本化 JSON 种子；开发时使用 Python 标准库离线整理，生产启动直接由 Node 导入。保留来源、原图摘要和未知辣椒标记，不将历史结果作为识别真值。
2. 在网站内建立独立菜品、菜单来源、供应记录、同步任务及租约表。菜品 ID 稳定，名称仅作 NFC、空白和大小写归一；不合并相近名称或拆套餐。统一使用固定版本 `pinyin-pro` 和词组覆盖生成 A–Z、拼音及首字母。
3. `recipe.html` 扩展为「全部菜品 / 菜品评价 / 每周食谱」。目录支持 A–Z 索引、搜索、防抖、中文输入法、高亮、URL 恢复和各类空/失败状态；评价接口和每周图片上传继续运行。
4. 开发者后台配置 OpenRouter 或 HTTPS OpenAI 兼容提供商、API Key、视觉模型。网站测试真实图片读取与严格 JSON 输出后，才允许开启自动同步。Key 在服务器端加密，主密钥自动生成，接口只返回掩码。
5. 同步时间由 developer 自行设置 HH:mm，默认 08:00，时区固定 Asia/Shanghai。修改时间持久化并重新计算下一次；当天已经自动触发或新时间已过则次日执行，不立即补跑、不终止当前任务、不使模型测试失效。每天最多自动触发一次，启动时补最近一次有效遗漏时刻。
6. Node worker 直接读取学校官网 `classid=36`，遵守 robots、固定源范围、限速、超时和熔断；按分页发现停机期间新增文章。生产不依赖另一台服务器、相邻仓库、Python、OCR 模型或本地命令行工具。
7. 原图 → 布局与表头 → 带上下文的重叠区块 → 视觉 JSON → 八字段校验 → 整图覆盖复核。记录菜品坐标证据；截断缩小区块，语义不确定或漏项拒绝整篇发布。每篇通过后事务替换，失败保留旧数据。
8. 每次最多识别十篇，每篇最多二十分钟及一百次模型请求，重试也计入预算。保存发现队列、租约、逐篇结果和缓存；提供进度、停止、重试、原图、JSON、诊断及补图重试。
9. 使用隔离数据库与上传目录验证种子、权限撤销、密钥、调度、提供商错误、取消、原子发布和浏览器回归。人工核对至少三张真实菜单图，记录模型失败与有效数据的区别；验证仅安装 Node 依赖即可部署。

追加需求：active developer、super_admin、admin 可在网站内粘贴八字段 JSON 新建手动批次、编辑已发布菜单或已结束识图候选。格式校验与完整原图人工复核后整篇发布，版本及租约检查防止互相覆盖，审计随事务保存。提供商、Key、调度与同步写操作仍仅 developer；无需额外服务器。详细规则为根 `menu-json-rules.md`，可复现打包的 `szzx-menu.skill` 使 AI 使用自身视觉能力直接生成数组。
10. 更新 README、MAP、进度、UI 手册和验收记录；记录部署、备份与故障处理方法。实现完成后由用户决定提交与发布。

本轮范围不含菜品详情页、评价外键迁移、店铺关联或 #6–#10 的业务。
